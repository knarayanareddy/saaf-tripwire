## 2. Conformance to the named workflow

The build prompt named `cloudflare/security-audit-skill` and its six phases. The real skill (checked at
`github.com/cloudflare/security-audit-skill`) defines them as:

1. Reconnaissance → `architecture.md`, `coverage-ledger.json`
2. Coverage-led hunting → isolated hunters + coverage critics
3. Candidate validation → fresh verifier per candidate
4. **Structured output** → `findings.json` validated against `report-schema.json`
5. **Independent record verification** → fresh agents re-check source claims
6. Target-neutral reporting → `REPORT.md`, `FINDINGS-DETAIL.md`, `NEEDS-VALIDATION.md`

What this repo ships:

| Phase | Artifact in repo | Status |
|---|---|---|
| 1 Recon + ledger | prose in `docs/METHOD.md`, `skill/.../SKILL.md` | **not implemented** — no `architecture.md`, no `coverage-ledger.json`, no validator |
| 2 Coverage-led hunting | 16 static rules + `redteam/` | **replaced**, not implemented — rules substitute for hunters |
| 3 Candidate validation | `redteam/run.py` (tests the rules, not findings) | **absent as a workflow**; its output is not reproducible (R-03) |
| 4 Structured output | none | **absent** — no `findings.json`, no schema, no validator |
| 5 Independent record verification | none | **absent** — no verifier, no record cross-check |
| 6 Reporting | `docs/FINDINGS-REGISTER.md` | **rendered elsewhere**, points at `/home/user/saaf-review-org/machine/` and `findings-org/findings.json`; not derivable here |

The skill directory contains exactly one file, `skill/saaf-tripwire/SKILL.md`, 59 lines. The reference skill is
~20 files including two zero-dependency validators and a JSON schema. `grep -ri "cloudflare\|report-schema\|coverage-ledger\|validate-findings"`
over the repo returns nothing outside `.venv`: the named workflow left no trace in the implementation. What was
built is an independent re-derivation of the *ideas* in `docs/METHOD.md` — which is defensible as engineering,
but it is not the thing the brief asked for, and the README presents it as if it were. The skill is also not
installed where a Claude Code agent would discover it (`.claude/skills/<name>/SKILL.md`); it is a single file
under `skill/` with no plugin manifest or install step, so "use the skill" today means copy-paste the prompt.

## 3. Findings — my own, in severity order

Each finding has a deterministic reproduction in `docs/review/repro-2026-11-16.sh`.

### R-01 · HIGH · The CI gate can be switched off by the pull request it is gating

`tripwire scan` reads `.tripwireignore` **from the scanned tree** (`tripwire/cli.py:26,63`). In the GitHub
Action the scanned tree is the PR checkout. A PR that adds two lines

```
src/app.py
src/keys.py
```

turns a failing scan into `0 finding(s) ... exit=0`. `BROAD_PATTERNS` (`cli.py:19`) refuses only total
wildcards (`*`, `**`, `**/*`); per-path ignores are exactly what an attacker needs. I demonstrated a repo with
a live key and a `0.0.0.0` bind going from `exit=1` to `exit=0` with no code change.

This directly contradicts `pitch/QA.md` #7 ("Could an attacker switch the guard off? … We closed the ways we
found") and is the same *class* as SA-41, which the repo built TW-CI3 to catch: untrusted input controlling the
guard's own control flow.

**Fix:** resolve `.tripwireignore` (and the baseline) from the *base* ref, or sign/hash-pin them; fail the run
if either file differs from the base; never allow path ignores for files changed in the diff.

### R-02 · MEDIUM · The baseline is the same bypass with a friendlier name

`--baseline` loads a JSON file from the scanned tree (`cli.py:49`) and suppresses by fingerprint. I generated a
baseline for a repo with a secret and a public bind, then re-ran: `0 finding(s) ... Suppressed by baseline: 2`,
`exit=0`. In `action.yml` the baseline path is `$TW_PATH/$TW_BASELINE`, i.e. inside the checkout. Baselines are
legitimate, but their *content* must be reviewed and pinned, or they are a mute button.

### R-03 · HIGH (evidence integrity) · The red-team table does not reproduce, and the harness silently scans nothing

The documented regeneration command is `.venv/bin/python redteam/run.py`. Run inside the checkout, it produces:

| Rule | committed `RESULTS.md` | fresh run in-repo |
|---|---|---|
| TW-SEC1 | 13 tried, **0 evaded**, control 1/1 | 13 tried, **13 evaded**, control **0/1** |
| TW-LLM1 | 8 tried, **0 evaded** | 8 tried, **1 evaded** (`evades_typescript`) |
| TW-CI2 | 3 tried, **1 evaded**, control 1/1 | 3 tried, **3 evaded**, control **0/1** |

17 rows change. Root cause is precise and deterministic: `engine.tracked_files()` prefers
`git ls-files` (`tripwire/engine.py:10-14`); the case directories are generated under `redteam/TW-*/`, which
`.gitignore` excludes, so `git ls-files` returns `[]`. Rules that iterate `ctx.files` without a fallback
(`sec_secrets` via `files_of`, `llm_unfenced_prompt.py:357`) then see **zero files** and report nothing. Copy
the same tree to `/tmp` (no `.git`) and the fallback `rglob` runs: the committed numbers reproduce exactly.
So the rules are fine; the evidence harness is broken in the only environment where it is documented to run.

Consequences: (a) the "attacked until it stopped getting through" claim is false at HEAD; (b) `run.py` also
rewrites the tracked `RESULTS.md` and deletes/recreates case dirs, so running the documented command dirties
the tree; (c) the two remaining genuine evasions (`evades_typescript`, `evades_tojson_event`) are real gaps
that the committed table hides.

**Fix:** pass an explicit file list / force the `rglob` path in the harness; assert `n_files > 0`; write results
to a temp dir; make `RESULTS.md` generated-in-CI with a diff check.

### R-04 · HIGH (evidence integrity) · Two irreconcilable audits are blended in one README

| Quantity | README / METHOD / PITCH / `SUMMARY.json` | `HOW-IT-WORKS` / `FINDINGS-REGISTER.md` |
|---|---|---|
| repositories | 50 | 51 visible, 45 pinned (6 empty) |
| confirmed | 44 (6 high, 17 medium, **21 low**) | 65 (**5 critical, 32 high, 28 medium**, 0 low) |
| rejected | 40 | 84 (42 refutations, 38 static, 2 disproved, 1 baseline, 1 duplicate) |
| fixes proven | **44 of 44** | 38 flipped + 2 baselines; 24 swept never reproduced |
| probes | 114 | 40 executed + 24 swept |

These are not two views of one dataset: the severity distributions are incompatible (21 low vs 0 low), and the
fix count differs. Corpus A lives only in rules' `seen_in`, `docs/evidence/*.md` and `SUMMARY.json`; corpus B is
the shipped register. Nothing reconciles them, and the README's headline uses A while the register — the only
long-form evidence in the repo — is B.

### R-05 · HIGH (evidence integrity) · Recall claims cite finding IDs the shipped register does not contain

The register contains `SA-01 … SA-16` plus `G-P*/G3-*/G7-*/G8-*/G10-*`. The rules, evidence files and
`SUMMARY.json` score against `SA-20, SA-22–SA-25, SA-29–SA-35, SA-37–SA-39, SA-41`. All of those return
**0 hits** in `docs/FINDINGS-REGISTER.md`. Therefore:

- "27/29 in scope, 27 caught" **cannot be recomputed from anything in the repo** — its input
  (`~/saaf-redteam/work/findings/findings.json`) is referenced by `scripts/evidence.py:52` and not shipped.
- "32 of the 65 … including 22 of the 40 live-tested" **can** be recomputed from `register-match.json`, and it
  is internally consistent (22 executed + 10 static = 32). Credit where due — but it is a different audit.

A rule claiming "seen in SA-30" is therefore an unverifiable assertion, not evidence. This is precisely the
"claims never re-checked against source" failure the second opinion names.

### R-06 · MEDIUM · Nine of sixteen rules have evidence prose; seven do not, and the generator crashes

`docs/evidence/` has files for CI1, CI2, CI3, DEP1, GATE1, KEY1, LLM1, LLM2, SEC1. Missing:
**FS1, NET1, NET2, NET4, NET5, OUT1, OUT2** — seven rules that the README table nonetheless reports hits and
recall for. `python scripts/evidence.py` fails immediately with
`FileNotFoundError: '/home/user/saaf-redteam/work/repos'`. The README evidence table is a committed snapshot
that no reader can regenerate.

### R-07 · MEDIUM · Two rules violate the brief's "non-negotiable" test bar

`BUILD-BRIEF.md` requires every rule to ship ≥2 vulnerable and ≥2 safe fixtures plus a pytest. **TW-FS1** and
**TW-OUT2** have zero fixture directories and no test file (`tests/test_tw_*.py` has 12 files for 16 rules); no
test anywhere references either rule. The README claims "Each rule has examples that must trigger it and safe
examples that must not." These two rules — including the one the tool itself trips — can regress silently.

### R-08 · HIGH (scope) · The skill is a prose prompt, not the workflow it names

See §2. No schema, no ledger, no `findings.json`, no independent verifier, no stop condition, no reference to
the named skill. A 59-line prompt cannot enforce "the agent that finds a bug never confirms it" — the prompt can
*ask* for it, which is exactly the "theatre" risk the second opinion identifies.

### R-09 · MEDIUM · The guard follows symlinks, and a symlink can OOM it

`engine.tracked_files()` returns symlinks and rules read them. In a repo containing `leak.txt -> /etc/passwd`,
the engine returns the symlink and `read_text()` yields `root:x:...` — arbitrary operator-file read from an
untrusted repo, which is the exact defect TW-FS1 is written to catch. Worse, `z.txt -> /dev/zero` makes the
scan read unbounded data: with no cap I measured **exit 137 (SIGKILL, OOM)** in under 8 s; under a 1 GB
`ulimit` the rule dies with `MemoryError` and the whole scan exits 2. Either way a 2-line PR stops the scan
completing, and with no cap it can kill the CI runner before the 15-minute timeout.

This is not hypothetical: the self-scan reports it on the tool's own files
(`tripwire/util/llmscan.py:16`, `tripwire/util/webscan.py:29`) as **medium**, which sits below the default
`--fail-on high`, so it ships. "Tripwire passes its own scan" is true and also misleading — it passes with two
true positives unfixed, one of which I exploited.

**Fix:** skip `p.is_symlink()` and require `p.resolve().is_relative_to(ctx.root)`; cap bytes read per file; do
the same in the `rglob` fallback.

### R-10 · MEDIUM · The documented command does not run on a supported Python

`pyproject.toml` declares `requires-python = ">=3.10"`, but every documented invocation uses `python -P`,
which was added in **3.11**. On 3.10 the README's own command errors; the natural workaround — drop `-P` —
reopens the `sys.path` shadowing that SA-41/TW-CI3 exist to prevent. Either require `>=3.11` or ship a launcher
that enforces the isolation without `-P`.

### R-11 · MEDIUM · `check_quotes` proves substring presence, not evidential support

`check_quotes(..., min_chars=1)` accepts a quote if its normalised form is any substring of the source. Against
a real policy sentence, the quotes `"a"` and `"the"` are **accepted as grounded**; `"PASS"` and a fabricated
sentence are rejected. So a model (or an injected model) can satisfy the anti-fabrication control with a
one-character or stop-word quote while inventing the finding. The docstring treats emptiness as failure but not
triviality. **Fix:** default `min_chars` to ~24–40, require the quote to be unique-ish, and check that the
verdict's claim is entailed by the quoted span rather than merely present in the document.

### R-12 · LOW · Private-repo SARIF upload is misconfigured, by the repo's own comment

`.github/workflows/tripwire.yml:32` says "(Private repos also need `actions: read` for the SARIF upload.)" and
then does not grant it (`contents: read`, `security-events: write` only). 38 of the 51 target repos are
private, so the "findings inline on the PR" promise is the case least likely to work where it matters most.

### R-13 · LOW · Shipped materials contain unfilled template variables and overstatements

`pitch/QA.md` #6 and `pitch/PITCH.md` §5 still contain `{{RECALL}}`, `{{RULES}}`, `{{TESTS}}`. PITCH says "44
weaknesses confirmed. Each one has a test that fails before the fix and passes after" — the register says 24
are swept (not reproduced), 2 are baselines, and 38 flipped. This is the corpus-A/B split again, in the material
a judge reads first.

### R-14 · LOW · Three rules contribute nothing to recall, and fork PRs will fail the self-scan

TW-CI2, TW-DEP1 and TW-OUT2 have `recall = 0.0` in `SUMMARY.json` yet are presented alongside rules that hit.
Separately, `self-scan.yml` calls the reusable workflow with `tripwire-ref: ${{ github.sha }}`; for a fork PR
that SHA is the ephemeral `refs/pull/N/merge` commit, which is not fetchable by SHA from
`SAAF-Project/saaf-tripwire`, so the guard checkout is expected to fail. Contributor PRs would then fail for a
reason unrelated to their code (worth confirming on a real fork PR).

## 5. What the table missed

1. **The guard's own control plane is bypassable** (R-01, R-02). This is a *product* defect, not a
   methodology gap, and it invalidates the central claim "it stops the change before a bad actor can use them."
2. **The evidence base is internally inconsistent** (R-04, R-05). Two audits, two ID spaces, two fix counts —
   a reader cannot tell which numbers the rules were built from. This is more damaging than "no findings.json".
3. **The red-team evidence does not reproduce** (R-03), and the harness silently scans zero files in a git
   checkout. A security tool whose adversarial evidence is stale is worse than one with no such evidence,
   because it transfers unearned confidence.
4. **Two rules are untested** (R-07) against the brief's own non-negotiable bar.
5. **The guard is susceptible to the exact class it preaches** (R-09): symlink read and OOM, flagged by its own
   self-scan and left unfixed.
6. **Supported-version drift** (R-10) that silently disables the `-P` isolation.

## 6. What would make the claim true (ordered backlog)

**Product (do first — these are exploitable today)**
1. Move `.tripwireignore` and the baseline to a trusted, hash-pinned source; fail if they change in the diff.
   Add a regression test per bypass.
2. Skip symlinks and enforce `resolve().is_relative_to(root)`; cap bytes read per file. Fix the two self-scan
   mediums and turn the self-scan to `--fail-on medium`.
3. Raise `requires-python` to `>=3.11` (or ship a launcher), and make `action.yml` pass `-P` implicitly.
4. `check_quotes(min_chars>=24)` by default; add a test where a 1-char quote must fail.
5. Add fixtures + pytest for TW-FS1 and TW-OUT2; add the missing seven evidence files or drop them from the
   README table.

**Workflow (what the brief actually asked for)**
6. Ship the six phases as artifacts, not prose: `coverage-ledger.json` + validator; `report-schema.json` +
   `findings.json` with three verdicts (`confirmed`, `needs_validation`, `rejected`); `REPORT.md` /
   `FINDINGS-DETAIL.md` / `NEEDS-VALIDATION.md` rendered *from* the records.
7. Make verification mechanical and independent: a `tripwire verify` that re-runs each probe id against a
   pinned SHA and a patched tree; a CI job that regenerates the evidence table and fails on drift; a record
   hash so producer and checker can be compared without shared context.
8. Pick **one** corpus. Either ship corpus A's `findings.json` and score the README against it, or rescore the
   rules against the shipped 65-record register and retire the `SA-20+` claims. Keep the ID space consistent.
9. State the stop condition: unit budget, "every unit covered or named out_of_scope", and a maximum passthrough.

## 7. Bottom line

- **As a guard**, this is a credible, well-tested 16-rule scanner with a strong runtime fence and a genuinely
  good determinism/fail-closed story. It would catch real SAAF defects today.
- **As the deliverable described in the build prompt**, it is a method document plus a scanner. The two phases
  that make the workflow trustworthy — machine-readable records and independent re-verification — are absent,
  and the evidence it does ship cannot be reproduced or reconciled.
- **The supplied second opinion** correctly identifies the verification/provenance hole and the self-grading
  problem. It overstates the omissions (reporting is present; the guard covers far more than the six named
  classes), and it misses the two things that matter most operationally: **the gate is bypassable** and
  **the evidence base contradicts itself**.

### Residual risk and what is still open

- **Local scans still honour an in-repo `.tripwireignore` by design** (documented in the repro's first section).
  The trust boundary is CI, where the base commit is authoritative. For local runs against untrusted code, pass
