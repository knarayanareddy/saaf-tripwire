# Self-audit — SAAF Tripwire, 2026-11-16

The build was asked to audit 50 repositories with a six-phase method. This document runs the **same
method against the guard itself**: reconnaissance and a coverage ledger, attack-class hunting, adversarial
disproof, schema-validated findings, independent verification, and a derived report. The yardstick is the
guard's own claims — README, `HOW-IT-WORKS.md`, `action.yml`, `skill/saaf-tripwire/SKILL.md` and the rule
contract in `tripwire/model.py`.

**Rule for this audit:** a record is `confirmed` only with an executed probe and both observed outputs;
without one it is `rejected` (with the observation that killed it) or `needs_validation` (with the exact
unresolved fact). No severity without a probe.

Artifacts, all under `docs/self-audit/`:

| Phase | Artifact |
|---|---|
| 1 | `architecture.md`, `coverage-ledger.json` |
| 2–3 | `findings.json` (9 confirmed, 5 rejected, 3 needs_validation) |
| 4 | `report-schema.json`, `validate.py` |
| 5 | `probes/probes.py` (14 probes, 14 pass) |
| 6 | `REPORT.md`, `FINDINGS-DETAIL.md`, `NEEDS-VALIDATION.md` (generated by `render.py`) |

---

## Phase 1 — Reconnaissance and coverage ledger

The target is a deterministic, offline Python engine: `tripwire/engine.py` walks files, 16 rule modules
consume `Context`, `tripwire/report.py` renders text/JSON/SARIF, and four delivery surfaces wrap it (CLI,
composite action, reusable workflow, skill prompt). The untrusted inputs are the scanned worktree, the
scanned repo's `.git` (config, attributes, objects, filenames), the in-repo control plane
(`.tripwireignore`, baseline), and — for the action — the package index and caller inputs.

`coverage-ledger.json` has **18 units: 15 covered by an executed check, 3 out of scope with a named reason**.
`validate.py` enforces the ledger's terminal states; `needs_validation` is deliberately not a ledger status
(the skill's rule), so an unresolved question lives in `NEEDS-VALIDATION.md` instead of being counted as
coverage.

Three findings about the build's *own* method, before any code:

- **R-08 stands, and this audit is the proof.** There is no `findings.json`, no coverage ledger, no schema
  validator and no independent verifier in the product. The engine emits findings and a human/agent reads
  them; nothing re-checks a claim against the source. This directory had to supply those phases. They are
  audit artifacts, not a shipped capability.
- **There is no formal spec to compare code against.** `spec-to-code-compliance` had to use the README's
  behaviour claims, `action.yml`'s inputs/exit codes, `SKILL.md`'s tool contract and `model.py`'s rule
  contract as the spec. That is sufficient to catch contradictions (several were: see R-10, R-12, TW-A7/A8)
  but it is not a spec.
- **The AI/LLM class is relevant without calling an LLM.** The `llm_*` rules inspect *audited* code for
  unvalidated model output and unfenced prompts; the guard itself never calls a model. The class is about the
  trust boundary in the audited system, not about the scanner's runtime. The one place the guard *does* sit
  on that boundary is its own output: finding evidence is consumed by an agent (TW-A6).

## Phase 2 — Attack-class hunting

| Class | Probed | Outcome |
|---|---|---|
| **web-protocol-and-auth** | git as an execution surface on an untrusted repo: `diff.*.textconv`, `core.fsmonitor`, hooks path, external diff | **TW-A1, TW-A2 confirmed high** (code execution); hooks path does not fire on `ls-files` |
| **client-side** | filenames/messages into CI logs and SARIF: newlines, `::` workflow commands, quotes, C1 controls | **TW-A5 confirmed medium** (forged annotation); SARIF JSON escaping held (TW-R4 rejected) |
| **data-isolation** | symlink/device reads, parent-repo paths, control-plane files | R-09 regressions hold; **TW-R3 rejected** (realpath containment + `S_ISREG`); control-plane bypass fixed in the review (R-01/R-02) |
| **resource-exhaustion** | pathological regex inputs, `/dev/zero`, 4 MB documents, history memory | **TW-R1 rejected** (0.47 s over 5 × 0.5 MB pathological files); **TW-N2/N3 need validation** (very large history / 100 MB documents unmeasured) |
| **ai-and-llm** | fence neutralisation, instruction text in evidence, quote grounding | **TW-A6 confirmed medium, mitigated**; **TW-R2 rejected** (11 payload families, no `<`/`>` survives) |
| **supply-chain-and-release** | action build/install, dependency declaration, pins, permissions | **TW-A7 low, TW-A8 high, TW-A9 low** — the shipped action could not run on a clean runner |
| **business-logic** (general) | git failure handling, shallow clones, rule isolation, base-ref config | **TW-A3, TW-A4 confirmed** (fail-open history, shallow false clean); rule-crash isolation holds (TW-R5) |

Notable variant: the history rule was hardened for `textconv` first, then the same "git runs auditee
config" question was asked of `git ls-files` — which is the every-scan path and needed a second fix. That is
the variant-analysis lens paying for itself.

## Phase 3 — Adversarial disproof

Candidates raised and killed by observation (full text in `findings.json`):

| ID | Candidate | Killed by |
|---|---|---|
| TW-R1 | ReDoS in rule regexes | 16 rules over 5 pathological 0.5 MB files: 0.47 s; no rule over 0.2 s; 4 MB inputs linear |
| TW-R2 | fence escape via nested/uppercase/zero-width markers | 11 families, 0 surviving `<`/`>` or closing marker |
| TW-R3 | symlink/device read outside the root | `is_safe_file` refuses symlink, `/dev/zero`, and paths outside root; regular file accepted |
| TW-R4 | second SARIF result / broken JSON via filename | one result, valid JSON, URI a single escaped string |
| TW-R5 | crashing one rule hides the rest | rule error forces exit 2 and the other rules' findings are still emitted |

Two candidates were **downgraded, not dismissed**: the quote-grounding check is a verbatim check, not
entailment (documented limitation, R-11 floor), and the prompt-injection surface is the intended evidence
contract (mitigated, not removed).

## Phase 4 — Structured, schema-validated output

`findings.json` is validated against `report-schema.json` by `validate.py`, with the schema's conditional
requirements enforced explicitly (no third-party `jsonschema`):

- confirmed → severity, non-empty trace, probe command + expectation, observed before/after, fix, status;
- rejected → the refutation string;
- needs_validation → the exact unresolved fact **and no severity**;
- unique `TW-[ARN]\d+` ids; class from the allowed set; ledger units terminal (`covered` needs check+result,
  `out_of_scope` needs reason).

Result: **VALID — 9 confirmed, 5 rejected, 3 needs_validation; ledger 18 units (15 covered, 3 out of scope)**.

This is the phase the product does not have. It exists here, for this audit, and dies with the directory.

## Phase 5 — Independent verification

`probes/probes.py` re-creates every hostile repo from scratch under `mktemp`, runs the attack, and asserts
the post-fix behaviour. It is a separate process from the engine and does not import the rules' internals
(except the fence/safeio unit probes, which call those pure functions directly). Every confirmed record has
a probe; `A8` additionally builds a clean venv and installs only the pinned dependency.

**14/14 pass.** Representative observations:

```
A1 PASS  raw git log runs the driver=True; tripwire scan executes it=False
A2 PASS  raw ls-files runs fsmonitor=True; tripwire scan does=False
A3 PASS  exit=2; fail-closed message=True
A4 PASS  full: 1 finding(s) exit 1; depth-1: exit 2 shallow-hint=True
A5 PASS  log line starts with '::'=False; raw newline injected=False; SARIF one safe uri=True
A6 PASS  auditee text reaches evidence=True; skill declares output untrusted and requires fencing=True
A7 PASS  no build of the guard=True; dependency declared and pinned=True
A8 PASS  clean venv: version exit 0; scan exit 1 (secret found; no import error)
A9 PASS  comment+continuation fixture: 0 findings; unpinned continuation: 1
```

The separation is real **for this audit** — but it is not a property of the product. The same engine that
emits a finding also decides whether it is suppressed and what the exit code is; there is no second opinion
inside the guard.

## Phase 6 — Report, verdict, stop condition

**Does the guard hold up?** Its detection rules do; its delivery and evidence integrity did not.

- Two ways for a scanned repo to execute code as the CI user (`textconv`, `core.fsmonitor`) — both fixed by
  one choke point, `tripwire/util/gitcmd.py`.
- History could fail open, and a shallow clone could read as clean — both now fail closed with exit 2.
- A filename could forge a GitHub annotation — control characters are collapsed in text, SARIF and errors.
- The action could not start on a clean runner (undeclared PyYAML + `--no-deps`) — dependency declared and
  pinned; the guard is staged, not built.
- Finding evidence still carries auditee instructions into the agent — mitigated by the skill's
  untrusted-data contract, not removable without destroying evidence.

**Stop condition met:** 15/18 ledger units covered by an executed check, 3 named out of scope, every confirmed
record has a passing probe, every rejected record has its refutation, and the 3 unresolved facts are named
with the check that would settle them. No open-ended fuzzing was attempted.

**Where it still fails its own bar:** the product ships no phase 4–6 machinery (R-08); its "independent"
verification is a human reading a report; and its evidence channel is a prompt-injection surface by design.
Those are recorded, not papered over.

## Verification (run from the repo root)

```sh
python docs/self-audit/validate.py          # VALID — 9 confirmed, 5 rejected, 3 needs_validation
python docs/self-audit/render.py            # regenerates REPORT.md / FINDINGS-DETAIL.md / NEEDS-VALIDATION.md
python docs/self-audit/probes/probes.py     # 14/14 probes passed
python -m pytest -q                         # 287 passed
python -P -m tripwire scan . --no-history --fail-on medium   # 0 findings
```

`--no-history` is required in this checkout because it is shallow; the history scan intentionally fails
closed (exit 2) rather than report a false clean. In CI the reusable workflow checks out with
`fetch-depth: 0`, so history is scanned.
